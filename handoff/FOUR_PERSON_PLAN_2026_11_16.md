## 2 我们答辩到底讲什么

### 一句话主线

**我们希望从多视角照片得到可查看、可导出的三维网格，并用可追溯的对照实验检查几何优化是否真正有效。**

这是项目目标和答辩组织方式，不是对当前完成状态的提前宣告。答辩内容应在结果冻结后根据证据改成实际完成的版本。

### 五段叙事

| 段落 | 要回答的问题 | 应展示什么 | 不能越过的边界 |
|---|---|---|---|
| 1 为什么做 | 多视角照片如何变成后续能使用的三维模型？任务书希望解决什么？ | 原任务目标、输入照片、用途示意 | 不把所有 3DGS 都概括为不能生成网格；说清本项目目标 |
| 2 怎么建立流程 | 我们用什么已有方法把照片和相机变为模型、网格、纹理？ | SuGaR 流程图、环境与模型来源、实际输出 | 现成 SuGaR 能力归属上游；本组恢复、适配、集成工作独立说明 |
| 3 为什么进一步比较 | 能展示模型后，几何指标是否改善，能否公平比较？ | G-GS baseline 与早期 occupancy M1 的同协议对照 | SuGaR 展示与 G-GS/M1 是两条管线；不能说 M1 已移植进 SuGaR |
| 4 我们发现了什么 | 哪些指标变好，哪些没变好，结果有没有波动或版本问题？ | 原始 JSON、固定设置、同视角图、局限 | 历史核算／新评价／新训练分开；不只报有利指标，不把训练视角当测试视角 |
| 5 后续如何判断 | TGS 探索给了什么教训，下一步为何先核验？ | v29 校准与留出结果并列、v30 固定输入核验设计 | 留出退化必须保留；v30 尚是提案，不能讲成已完成算法 |

故事的因果关系是“实际重建需求 → 可用流程 → 几何质量需要验证 → 实验暴露局限 → 用更严格的验证决定下一步”。不把路线变化包装成预先设计好的成功链条；说明哪些选择来自真实的失败、资源和证据。

### 贡献分类与答辩用词

- 上游能力：SuGaR、G-GS、TGS 的已有表示／渲染／导出能力，引用来源。
- 本组工程工作：只列已完成的环境迁移、资产恢复、流程适配、展示集成和操作文档；没验证的仍写待验证。
- 本组实验与分析：明确哪部分代码／损失是本组改动，哪部分是继承代码；黄与朱逐项核对。重算历史 JSON 不等于独立重现实验。
- 本组研究探索：v29 的负结果和数值诊断有记录价值；论文级新颖性、泛化提升和完整训练收益不能仅凭这些记录推出。

可用的诚实表述：“在保留的历史记录中观察到……”“我们在固定设置下重新评价了……”“接收环境目前通过了……”“这项探索没有取得留出视角收益，所以后续先检查……”。只有对应证据齐全才使用第二、第三类完成式表述。

## 7 Git 同步方式

### 文件归属

建议每人维护一个主要文件，减少冲突；以下是待创建的工作文件名，不代表已经有内容：

```text
handoff/team/
  a_story.md                 刘：答辩文字骨架与要求核对状态
  b_environment.md           孙：环境／硬件／路径与检查记录
  b_run.md                   孙：实际命令和运行回执索引
  c_metrics.md               黄：历史指标核算及数字差异
  c_evidence.md              黄：结论到证据的映射
  d_assets.md                朱：最小资产与版本交接
  d_tgs.md                   朱：研究结论卡和核验协议
  STATUS_2026_11_16.md        刘汇总，其他人通过 PR 提供信息
  STATUS_2026_11_17.md        刘汇总，其他人通过 PR 提供信息
```

小型、脱敏文本放 Git；数据集、checkpoint、大视频按已有资产方案存放，只提交路径／下载入口／大小／SHA256。账号、令牌、学号、审批截图、含个人信息的正式报告在团队受控目录保存，不提交公开仓库。

### 每日操作

先检查 `git status`；有未提交改动先自行提交或妥善保存，不用 reset／clean 强行同步。工作区干净时，在已登录且有仓库权限的终端从最新 main 建自己的分支，例如孙使用：

```bash
git switch main
git pull --ff-only origin main
git switch -c docs/sun-environment-2026-11-16
# 编辑本人负责的文件，检查差异后只加入本次文件
git add handoff/team/b_environment.md
git diff --cached
git commit -m "docs: record receiver environment and blockers"
git push -u origin docs/sun-environment-2026-11-16
```

这个分支已存在时用 `git switch`，不要重复 `-c`。其他成员分别用 `docs/liu-story-2026-11-16`、`docs/huang-metrics-2026-11-16`、`docs/zhu-assets-2026-11-16`。第二天延续尚未合并的任务分支；已合并则从最新 main 建新分支。

在 GitHub 建 PR，写“改了什么／证据在哪里／哪些尚未验证／需要谁看”。孙的 PR 请朱看，朱的资产 PR 请孙看，黄的指标 PR 请朱看、刘确认表述，刘的故事 PR 请黄和朱看。至少一人核对后由负责人或有权限者合并；不强推、不覆盖别人的文件。同步到 Git 不等于完成验收，PR 状态和技术验收状态分别记录。

Git 不熟可用网页编辑自己负责的 Markdown 并选择新分支后发 PR；不会运行 Git 命令不妨碍先写记录。不能把所有进度只留在聊天里。

